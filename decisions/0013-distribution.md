# ADR-0013: The schema is the validation; releases carry the artefacts

- **Status:** Proposed
- **Date:** 2026-07-28
- **Audience:** Informatics reviewers — implementation detail. Safe to skip if you're reviewing the science.

## Context

Two problems arrived together.

**Consuming the register takes work.** Answering "is this a Southern Resident", "was this
animal alive then", or "the moderator typed `T090s` — what is that" means walking a graph,
applying a precedence rule, and merging two name sources. Every consumer would implement
those, and would implement them slightly differently, which is the failure this register
exists to prevent.

**`bin/validate.py` had become a hand-rolled constraint engine** — three hundred lines of
nested loops re-deriving foreign keys, enums, uniqueness and NOT NULL, none of which the
consumer ever sees.

[ADR-0001](0001-tsv-in-git-as-source-of-truth.md) argued "TSV versus a database" as if it
were one decision. It is two: **what do we edit and review**, and **what do we ship**. Its
reasoning — reviewable diffs, git as an audit trail — is entirely about the first. It said
nothing about the second, and by not distinguishing them it implied an answer to a
question it had not considered.

## Decision

**TSV in git remains the source of truth.** ADR-0001 is unchanged on that point.

**`schema.sql` is the normative statement of the register's constraints**, and the build
is the validation: `bin/validate.py` loads the TSVs into a SQLite database built from that
schema, and a malformed row is rejected by the database rather than by bespoke Python.

**Artefacts are attached to GitHub releases**, not committed as binaries and not published
to GitHub Packages.

## Implementation

### The schema carries the constraints

Twelve classes of bad data that previously needed hand-written checks are now declarative:

```sql
entity_id TEXT PRIMARY KEY CHECK (entity_id GLOB 'SSA:[0-9][0-9][0-9][0-9][0-9][0-9][0-9]')
kind      TEXT NOT NULL CHECK (kind IN ('individual','group','taxon'))
CHECK (kind <> 'taxon' OR taxon_id IS NOT NULL)     -- ADR-0008
CHECK (label NOT LIKE '%?')                          -- ADR-0009
PRIMARY KEY (entity_id, recorded, effective)         -- ADR-0006 precedence ties
CHECK ((replaced_by IS NULL) <> (consider IS NULL))  -- ADR-0010 exactly one pointer
```

SQLite stores the schema text verbatim, comments included, in `sqlite_master` — so the
shipped file explains itself:

```sh
sqlite3 register.db 'SELECT sql FROM sqlite_master'
```

One constraint needed contortion, and it is the only real wart. "A container must be a
group or a taxon" requires a composite foreign key against `UNIQUE(entity_id, kind)`, so
`membership` carries a denormalised `group_kind` column. **Curators never maintain it; the
build populates it.** It exists in the database and not in the TSVs.

This is not a net reduction in lines — roughly 320 lines of Python became 205 plus 220 of
DDL. The gain is that the constraints are now declarative, stated once, and *published*:
the DDL is a document a consumer reads, which the Python never was.

### What stays procedural

Three things SQL cannot state declaratively, now expressed as queries rather than loops:
cycle detection (a recursive CTE), orphan detection, and the rule that `names.tsv` must not
repeat a preferred label.

Diagnostics stay too, and that is deliberate. A bare `FOREIGN KEY constraint failed` is
useless to a curator reviewing a pull request, so rows are inserted individually and
reported as `entities.tsv:14: SSA:0000101: <constraint>`. Losing that would trade a
curator's afternoon for an engineer's tidiness.

### Views, so the intelligence ships once

`dist/` carries the derived facts as TSV, generated by `--write-dist` and committed
(they are text and they diff):

| View | Answers |
|---|---|
| `ancestor.tsv` | C5, C6 — the transitive closure, precomputed |
| `current_status.tsv` | C4 — the `(recorded, effective)` precedence rule from ADR-0006 |
| `searchable_name.tsv` | C2 — preferred names and every alternate, in one place, each carrying the entity's label, kind and rank so two candidates can be told apart |
| `retired.tsv` | C9 — deprecations, marked `automatic` or `needs-human` |

Generated files are sorted in Python, not with `ORDER BY`. They are committed and CI
compares them against a fresh build, and SQLite versions order an unordered recursive CTE
differently — which made the artefact spuriously dirty on the first CI run. Sorting
outside the engine is version-independent. **Any committed generated artefact needs a
deterministic order**, and it is worth knowing that the freshness check is what surfaces
it.

`current_status` is the point of the exercise. Without it, every consumer reimplements a
precedence rule whose subtlety is that ordering by `effective` alone is wrong. With it,
they `SELECT`.

### SQLite, not DuckDB

DuckDB has the better feature set and its storage format has not been stable across
versions. For a publication whose thesis is "still readable in ten years", that is
disqualifying. SQLite's format is an explicit long-term archival target.

Nothing is lost: DuckDB attaches SQLite directly (`ATTACH 'register.db' (TYPE sqlite)`),
and reads the TSVs directly too, with no build step at all.

### Releases, not Packages

GitHub Packages has **no generic file registry** — the API rejects `package_type=generic`,
its ecosystems are npm, RubyGems, Maven, NuGet and ghcr.io, and `gh` has no `package`
command. More to the point, OrcaSound's server is Elixir and no GitHub Packages ecosystem
serves Elixir at all.

Releases do what was wanted, with permanent URLs that need no client:

```
https://github.com/salish-sea/animals/releases/latest/download/register.db
https://github.com/salish-sea/animals/releases/download/2026.07.1/register.db
gh release download 2026.07.1 --repo salish-sea/animals --pattern 'register.db'
```

This answers [Q11](../docs/open-questions.md): that URL *is* the stable address, and it
carries no hosting commitment.

Release assets:

| Asset | For |
|---|---|
| `register-tsv.tar.gz` | Both consumers. Postgres ingests it with `COPY`. |
| `dist/*.tsv` (in the tarball) | The derived views, same treatment |
| `register.db` | Third parties, notebooks, `datasette`. Neither consumer runs it. |
| `schema.sql` | The constraint contract, to be translated into each consumer's own DDL |
| `SHA256SUMS` | Provenance |

### Provenance without a lockfile

A package manager would have given integrity hashes and pinning for free, which is what
[ADR-0006](0006-valid-time-in-data-assertion-time-in-git.md) wants recorded as
`register_edition` on every annotation. Releases do not. So: publish `SHA256SUMS`, and
have consumers record the tag **and the digest they verified**. That is more honest than a
lockfile anyway, since it survives the file being fetched from anywhere.

### Cadence, and who cuts a release

**A release is a tag push, never a push to `main`.** `release.yml` triggers on a CalVer
tag; `validate.yml` runs on every push and pull request and publishes nothing. Cadence is
therefore a decision someone makes, not a consequence of merging.

**Releases are cut on demand, and during active development that may be several a day.**
CalVer's third component is a sequence within the month, so `2026.07.1` … `2026.07.14` is
an ordinary month rather than a pathological one. In steady state the rate falls to
whatever the roster does — census-driven, so a few times a year, plus corrections. Cadence
tracks demand in both directions; it is not a schedule. [ADR-0014](0014-a-publication-not-a-service.md)
depends only on there being editions to be stale between, not on how often they arrive.

Frequent tagging costs consumers nothing, and this is the reason the question of release
churn dissolves rather than needing a `release` branch to answer it: **nothing is dragged
along by a tag.** Both consumers pin a tag and record a digest, so each moves when it
decides to. Only `releases/latest/download/` tracks the tip, and that is for third
parties and notebooks that asked for exactly that. A release branch would also have
nothing to hold — it earns its keep when fixes must be backported to a maintained old
line, and corrections here are append-only and forward-only
([ADR-0006](0006-valid-time-in-data-assertion-time-in-git.md),
[ADR-0010](0010-identifiers-are-never-reused.md)), so no old edition is ever patched.

**P. Abrahamsen cuts releases today**, which works only because tagging and curation are
currently the same person. Widening that — S. Veirs is the obvious second — means making
the authority delegable without also handing over the ability to publish an arbitrary
artefact under the register's name. Unresolved; see [Q25](../docs/open-questions.md).

## Consequences

- Both consumers are Postgres — OrcaSound runs `ash_postgres`, SalishSea.io runs Supabase
  — so neither will ever *query* the SQLite file. The TSVs are the integration path and
  the `.db` is a byproduct that happens to be useful to others. Building it is still
  worthwhile because it is *how the constraints get checked*.
- **Both consumers consume the same way**: a released artefact at a pinned tag, with the
  tag and digest recorded. SalishSea.io's tight coupling
  ([ADR-0012](0012-relationship-to-the-salishsea-io-catalogue.md)) is a statement about
  the model — it holds no identity of its own — not about the transport. One distribution
  path means one path to keep working.
- `schema.sql` is not a schema either consumer adopts. Both have their own migration
  systems and neither wants a foreign one imposed. It is a contract to translate.
- The build is now load-bearing: a broken build means no artefacts. The TSVs remain
  fetchable from the repository regardless, which is the fallback.
- CI can finally make good on ADR-0001's claim that committed output matches a fresh
  build, because there is now a build.

## Alternatives considered

- **DuckDB as the shipped format.** Better queries, unstable file format. Rejected above;
  it remains the better *tool* and can attach what we ship.
- **Publishing an npm package to GitHub Packages.** Would give lockfile pinning and
  integrity hashes — genuinely valuable — but the consumer that matters is Elixir, so it
  would serve the wrong half of OrcaSound.
- **Committing `register.db`.** Makes git history heavy and unreviewable for a file that
  is fully derived. Release assets are the right home for a binary.
- **Keeping the hand-written validator.** Works, but the constraints stay private to this
  repository, and a consumer wanting to know what is guaranteed has to read Python.

## Open questions

- Should `dist/` artefacts embed the commit they were built from? Yes, almost certainly —
  it makes an exported snapshot self-describing. Not yet done.
- Should `--strict` gate a release? It is not wired to one today — `release.yml` runs the
  ordinary validator — so the forcing function this ADR wondered about is not currently
  in force. It also sums two unlike warnings: 69 `SEED` rows, which are provenance debt
  retired by citing a source, and 13 unreachable entities, which are a modelling gap
  ([Q1](../docs/open-questions.md)) that no amount of verification will close. Gating on
  the total would block every release on an unrelated question. The alternative to a gate
  is to have each edition state its own warning counts, so a consumer can see how much of
  it is unverified instead of being promised that none of it is.
